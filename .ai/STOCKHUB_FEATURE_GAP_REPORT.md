# StockHub Feature Gap Report

**Audit date:** 2026-10-23  
**Scope:** Read-only inspection of the checkout at `/home/giahoang/dev/plugin_shopify/stockhub`, product requirements in the request, Sprint 5.1–5.4 reports, tests, Shopify app configuration, routes, Prisma schema/migrations and release-readiness notes. No code, DB, Shopify, Git history, or remote app state was changed by this audit.

## Executive summary

StockHub is a real Shopify embedded-app codebase with working source paths for authenticated, shop-scoped product reads, CSV receipt creation, import merge/resume, import history and read-only Shopify verification. It is **not release-ready** based on this checkout: there is no usable live app URL/session here, the Shopify config still names `https://example.com`, and the sprint reports explicitly leave embedded GUI acceptance pending. Automated tests and source checks are useful evidence of contracts, not proof that Shopify installation, product/inventory mutations, or merchant workflows succeeded end to end.

The checked-out project files are all **untracked** and `git rev-parse HEAD` cannot resolve a commit. Consequently the checkout itself cannot prove a clean baseline or map files to a specific commit. Sprint 5.1–5.4 outcomes below are verified against their reports and current source artifacts, but historical test counts/verdicts are **report-recorded, not rerun in this audit**. Treat the sprint-by-sprint claims as corroborated documentation, not a Git-derived release artifact.

### Status key

- **Implemented:** the requested capability exists in the current source with useful evidence.
- **Partial:** a limited or guarded slice exists; important requested behavior or acceptance is missing.
- **Missing:** no implementation found (or only an honest placeholder).
- **Blocked:** implementation/live acceptance cannot be established from this checkout or available environment.
- **Priority:** P0 blocks safe/live operation or core security; P1 needed for the promised core product/release; P2 later roadmap capability.

## Shopify compliance / release gates observed

The Shopify CLI 4.9.4 fetched the current App Store AI self-review requirement list during this audit. The app has no extension directory other than `.gitkeep`, so theme, payment, purchase-option, checkout customization, sales-channel and post-purchase conditional groups do not appear applicable from the current files. Opt-in groups were not evaluated because they were not requested. Applicable policy/security requirements still need full pre-submission review; this feature audit is not Shopify's official review.

Evidence-positive, locally checkable patterns: Shopify SDK session/authentication, declared access scopes, webhook signature authentication through the SDK, and privacy-topic subscriptions/handlers. Needs human/remote verification: valid hosted HTTPS/TLS and callback URL, real installation/session-token behavior, production scope grants, real Shopify-signed compliance webhook delivery, app-store/listing statements, and actual merchant workflow outcomes. `shopify.app.toml` currently contains a placeholder application URL, which blocks live acceptance here. `RELEASE_READINESS.md` also records one Low Shopify security finding for missing dependency security automation.

## Recommended backlog by business dependency

1. **P0 — Establish a runnable, isolated Shopify acceptance environment.** Resolve valid dev app URL and credentials through the owner's established configuration; install only to an approved test store; record store/API version/scopes and test-data cleanup boundaries. No production mutations.
2. **P0 — Validate authentication, least privilege and cross-shop isolation.** Exercise installation/re-auth, missing-scope fail-closed behavior, deep links and same-ID cross-shop denial across two test shops if available.
3. **P0 — Accept CSV → receipt → Merge in a disposable shop.** Verify malformed/ambiguous CSV and new/existing SKU paths; inspect product state, location activation and exact inventory deltas read-only after explicitly authorized actions. Capture request/receipt evidence and distinguish Draft Created from Inventory Activated.
4. **P0 — Reconcile the historical failed batch before any Resume.** Current readiness note says 10 rows are not certified safe to retry. Fresh read-only Shopify reconciliation is prerequisite; only proceed with any Resume after separate explicit approval. Prove idempotency under retry/unknown result.
5. **P1 — Complete Import History/Verify live acceptance.** Test server cursor/filter/deep-link behavior and cross-shop denial; verify-state must remain read-only; confirm FAILED never renders as COMPLETED and clipboard fallback works.
6. **P1 — Decide/implement Product Publishing and merchant approval.** This depends on verified product/inventory lifecycle and an explicit approval/ownership model; currently entirely absent.
7. **P1 — Decide Activity History product requirements and privacy policy.** Approve actor model, event/outcome taxonomy, durable retry identity, failure semantics, retention and shop-redaction before migration or persistence implementation.
8. **P1 — Close visual/accessibility/performance acceptance.** Record authenticated desktop/mobile GUI evidence for imports, dashboard, products and stores. Keep measured DB/browser performance separate from source call counts/parser microbenchmarks.
9. **P2 — Staff/team roles.** Define roles and staff identity behavior after deciding whether Shopify staff permissions meet the product need; add server-side authorization and audit coverage.
10. **P0 release gate — Shopify compliance and operational readiness.** Fix placeholder config in deployment environment; verify live TLS, app setup, current required webhooks, least privilege, dependency update automation and applicable Shopify requirements. Obtain owner acceptance and Shopify review where applicable before any RELEASE_READY designation.
